[^route53]: Route 53 répondait pour `bernat.ch` depuis décembre 2021. Je n'utilisais pas les sondes de disponibilité, trop chères. Je n'y hébergeais pas non plus la plupart de mes zones : les requêtes pour `haproxy.debian.net` m'auraient coûté à elles seules environ 10 $ par mois. Elle propose le [routage géographique][geographical routing], mais une fonctionnalité vraiment intéressante est le [DNS programmable][scriptable dns] : un bout de JavaScript personnalisé s'exécute à chaque requête pour calculer la réponse. Je fais tourner sept petites machines virtuelles NixOS pour héberger ce blog aux quatre coins du monde : Paris, Nuremberg, Ashburn, Singapour, San José, São Paulo et Sydney. Le DNS programmable de Bunny me permet de renvoyer les adresses IP des **deux serveurs les plus proches**. Le navigateur se rabat sur le second si le premier est en panne. ```js hl_lines="24 32" const servers = [ { ipv4: "45.90.160.60", ipv6: "2a0c:8881:5:100::1", latitude: 48.88, longitude: 2.22, }, /* […] */ { ipv4: "139.180.162.114", ipv6: "2001:19f0:5800:1855:5400:6ff:fef0:4c0a", latitude: -33.87, longitude: 151.21, }, ]; const families = { A: "ipv4", AAAA: "ipv6" }; const records = { A: ARecord, AAAA: AaaaRecord }; export default function handleQuery(query) { const type = String(query.request.queryType).toUpperCase(); const family = families[type]; if (!family) return []; // Position de l'utilisateur const location = query.request.geoLocation; // Liste des candidats let candidates = servers.map( (s) => new Server(s[family], s.latitude, s.longitude, 100), ); // Choix des deux serveurs disponibles les plus proches const selected = []; while (selected.length < 2) { const server = RoutingEngine.getClosestServer(candidates, location, true); selected.push(server); candidates = candidates.filter((s) => s.ip !== server.ip); } // Renvoi de leurs adresses IP return selected.map((s) => new records[type](s.ip, 3600)); } ``` Ce script repose sur la fonction [`RoutingEngine.getClosestServer()`][getClosestServer], qui renvoie le serveur disponible[^alive] le plus proche de l'utilisateur[^user]. Grâce à [Doggo][], vérifions que tout fonctionne comme prévu, au moins pour `A`[^a] : ```console $ doggo --gp-from="Amsterdam" A vincent.bernat.ch LOCATION NAME TYPE TTL ADDRESS Amsterdam, NL vincent.bernat.ch. A 3600s 45.90.160.60 vincent.bernat.ch. A 3600s 116.203.18.48 $ doggo --gp-from="Texas" A vincent.bernat.ch LOCATION NAME TYPE TTL ADDRESS Houston (TX), US vincent.bernat.ch. A 3600s 5.161.44.145 vincent.bernat.ch. A 3600s 149.28.219.155 ``` [^alive]: J'ai demandé à _bunny.net_ ce que « disponible » signifie, mais ils ont refusé de détailler la méthode employée. C'est un peu dommage, car [leur documentation][healthmonitoring] décrit les méthodes de surveillance pour les *smart records*. [^user]: L'utilisateur interroge Bunny DNS à travers un résolveur. En général, soit le résolveur se trouve à proximité de l'utilisateur, soit il transmet le sous-réseau de l'utilisateur via [EDNS client subnet][]. [^a]: N'utilisez pas ce script tel quel : `RoutingEngine.getClosestServer()` ne fonctionne qu'avec IPv4. Le [script final][complete code] contourne cette limite. Le défaut le plus gênant de cette méthode est qu'un utilisateur à Buenos Aires obtient à la fois São Paulo (1 600 km, 30 ms de RTT) et Ashburn (8 400 km, 140 ms de RTT). La plupart des résolveurs mélangent l'ordre des réponses : l'utilisateur risque donc de charger la page depuis Ashburn. Il serait possible de ne renvoyer que le serveur le plus proche, et même de remplacer l'enregistrement programmé par le routage géographique intégré à Bunny DNS. Mais si ce serveur devient indisponible, le navigateur n'a aucune solution de repli avant l'expiration du cache DNS. Même avec un TTL faible, une brève fenêtre d'indisponibilité subsiste. Les navigateurs modernes interrogent cet enregistrement pour obtenir des informations supplémentaires afin de joindre un serveur HTTP, notamment un autre port et le protocole applicatif (HTTP/2 ou HTTP/3). Chaque enregistrement possède une priorité. Il est ainsi possible de demander aux navigateurs de contacter d'abord le serveur le plus proche, puis de se rabattre sur le suivant si le premier est indisponible : ```zone vincent HTTPS 1 first.geo alpn="h3,h2" vincent HTTPS 2 second.geo alpn="h3,h2" vincent HTTPS 3 . alpn="h3,h2" ; Pour "first.geo" et "second.geo", Bunny DNS doit fournir les deux ; serveurs les plus proches via le routage géographique. first.geo A 45.90.160.60 first.geo AAAA 2a0c:8881:5:100::1 second.geo A 116.203.18.48 second.geo AAAA 2a01:4f8:1c0c:5eb5::1 vincent A 45.90.160.60 vincent A 116.203.18.48 vincent AAAA 2a0c:8881:5:100::1 vincent AAAA 2a01:4f8:1c0c:5eb5::1 ``` Cela semble la solution idéale ! Malheureusement, Chrome [ignore tout enregistrement dont la cible n'est pas `.`][cr40257146], d'où le dernier enregistrement en priorité 3. De plus, contrairement à un `CNAME`, Bunny DNS ne renvoie pas les adresses IP de `first.geo` et `second.geo` dans la section additionnelle. Le résolveur doit envoyer une première requête pour obtenir l'enregistrement `HTTPS`, puis une seconde pour résoudre `first.geo`. Les enregistrements HTTPS sont [encore trop récents][still too new] pour ce cas. Retour à la case départ ! 📐 [https dns record]: https://kalfeher.com/https-records-simple/ "Simple HTTPS Records" [rfc 9460]: rfc://9460 [cr40257146]: https://issues.chromium.org/issues/40257146 "Fully implement HTTPS-RR [40257146]" [still too new]: https://www.netmeister.org/blog/https-caniuse.html "Can I use HTTPS RRs?" ## La solution hybride En guise de compromis, le script renvoie les deux serveurs les plus proches s'ils se trouvent à une distance similaire de l'utilisateur. Sinon, il ne renvoie que le plus proche, avec un TTL réduit à 2 minutes. ```js export default function handleQuery(query) { const location = query.request.geoLocation; let candidates = servers.map( (s) => new Server(s.ipv4, s.latitude, s.longitude, 100), ); // Choix des deux serveurs les plus proches const selected = []; while (selected.length < 2) { const server = RoutingEngine.getClosestServer(candidates, location, true); selected.push(server); candidates = candidates.filter((s) => s.ip !== server.ip); } // Calcul de la distance entre chacun d'eux et l'utilisateur const [first, second] = selected.map((s) => GeoDistance.calculate(s, location), ); // Si le second est deux fois plus loin et à plus de 1000 miles du // premier, ne renvoyer que le premier avec un TTL de 2 minutes. if (second > 2 * first && second - first > 1000) { return [new ARecord(selected[0].ip, 120)]; } // Sinon, renvoyer les deux avec un TTL d'une heure. return selected.map((s) => new ARecord(s.ip, 3600)); } ``` Vérifions avec _Doggo_. Depuis Chicago, nous obtenons uniquement le serveur d'Ashburn avec un TTL de 2 minutes, tandis que depuis le Mexique, nous obtenons à la fois Ashburn et San José. ```console $ doggo --gp-from="Chicago" A vincent.bernat.ch LOCATION NAME TYPE TTL ADDRESS Chicago (IL), US vincent.bernat.ch. A 120s 5.161.44.145 $ doggo --gp-from="Mexico" A vincent.bernat.ch LOCATION NAME TYPE TTL ADDRESS Queretaro, MX vincent.bernat.ch. A 3600s 5.161.44.145 vincent.bernat.ch. A 3600s 149.28.219.155 $ doggo --reverse 5.161.44.145 149.28.219.155 NAME TYPE TTL ADDRESS 145.44.161.5.in-addr.arpa. PTR 7187s web05.luffy.cx. 155.219.28.149.in-addr.arpa. PTR 3600s web07.luffy.cx. ``` !!! Contrairement à Route 53, Bunny DNS ne permet pas de restreindre l'accès à une seule zone avec une politique d'accès fine. Comme cet usage n'exige ni haute disponibilité ni faible latence, j'ai remplacé Route 53 par [Hickory][], un serveur DNS écrit en Rust. Il prend en charge la [signature DNSSEC automatique][automatic dnssec signatures] et les [mises à jour dynamiques][dynamic updates backed by sqlite]. Sa configuration est simple : ```toml [[zones]] zone = "acme.luffy.cx" zone_type = "Primary" [zones.stores] allow_update = true type = "sqlite" journal_path = "acme.luffy.cx.sqlite" zone_path = "acme.luffy.cx.zone" # Clé privée pour signer la zone avec DNSSEC. Générée avec : # openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 [[zones.keys]] algorithm = "ECDSAP256SHA256" key_path = "/etc/hickory-dns.acme.luffy.cx.pem" # Clé TSIG pour signer les mises à jour de la zone. Générée avec : # openssl rand 32 [[zones.stores.tsig_keys]] algorithm = "hmac-sha256" key_file = "/etc/hickory-dns.acme.luffy.cx.update.acme.luffy.cx.tsig" name = "update.acme.luffy.cx." ``` Le [fichier de zone fourni][provided zone file] sert uniquement à initialiser la base au premier démarrage. Je délègue les défis DNS-01 à cette zone via des enregistrements `CNAME` : ```zone _acme-challenge CNAME bernat.ch.acme.luffy.cx. _acme-challenge.vincent CNAME vincent.bernat.ch.acme.luffy.cx. ``` [Lego][], le client ACME que j'utilise pour obtenir des certificats auprès de [Let's Encrypt][], répond aux défis DNS-01 en publiant des entrées avec le [protocole DNS UPDATE][dns update protocol]. Malheureusement, Bunny DNS ne peut pas publier d'enregistrement `DS` dans une zone[^ds]. J'en ai besoin pour sécuriser la zone `acme.luffy.cx` et la livraison des certificats. J'héberge donc la zone `luffy.cx` chez [deSEC][][^desec], un service d'hébergement DNS gratuit géré par une association à but non lucratif installée à Berlin. Je calcule l'enregistrement `DS` à publier dans `luffy.cx` à partir de l'enregistrement `DNSKEY` de `acme.luffy.cx` : ```console $ ZONE=acme.luffy.cx $ dig @nsupdate.luffy.cx $ZONE DNSKEY +noall +answer \ > | dnssec-dsfromkey -a SHA-256 -f - $ZONE acme.luffy.cx. IN DS 55628 13 2 4946E7508F20E15F1B577A231104B029A1A82E04699A80CD46ADCE31227EE81F ``` [^ds]: J'ai contacté le support de _bunny.net_ pour savoir quand ils prendront en charge la publication d'un enregistrement `DS` et j'ai obtenu une réponse sept minutes plus tard : ils ne savent pas. 😭 C'est frustrant, car ils gèrent automatiquement `CDS`, un enregistrement DNS qui annonce un enregistrement `DS` à la zone parente. Ils gèrent un côté de la délégation, mais pas l'autre. J'ai aussi signalé un problème dans la preuve de non-existence et ils m'ont fait une réponse détaillée le lendemain. [^desec]: Pourquoi ne pas utiliser deSEC pour les défis ACME ? Il est possible de [limiter ses jetons à un seul RRset][desec-scoping].
