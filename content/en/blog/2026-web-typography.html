We can avoid a runt—a word alone on the last line—with non-breaking spaces at the end of a paragraph and soft hyphens everywhere else. uuid: 6487cb90-bced-46df-9d8c-954c856dbdde cover: xkcd-1015.png tags: - web - programming-python src-ref: d2f41d4cd55080db009fbf1cab6ab8b5f5f1af52 css: - 2026-web-typography.css js: - 2026-web-typography.js --- Good typography is difficult to achieve on the web. Compared to typesetting engines like [LaTeX][] or [Typst][], the web still lacks a good line-breaking algorithm. The CSS directive `text-wrap: pretty` tries to improve the situation but is still [not implemented in Firefox][] and [produces eerie narrower paragraphs with Safari][webkit-pretty]. [Various][kp1] [good][kp2] [implementations][kp3] of the [Knuth-Plass algorithm][knuth-plass] exist in JavaScript, but they either reflow the text or delay its display. Instead, I taught my static site generator to manually insert soft hyphens and non-breaking spaces at tactical locations to achieve a predictable, okayish result. !!! The most notable "defect" for this paragraph is the word "_aigus_{lang=fr}": it may stay alone on the last line—or even be hyphenated. This is a "_runt_."[^runt] With hyphenation disabled, _runts_ are rarer, but the layout introduces "_bad rags_": a large blank space between the end of a line and the right margin, like in the second line when the paragraph width is 825 pixels. When the paragraph is justified, bad rags are translated into larger spaces between words. These traits make your text look poor and should be avoided.[^short] [^runt]: Various sources incorrectly refer to *runts* as *widows* or *orphans*. In [The Elements of Typographic Style][], Robert Bringhurst explains the difference between *widows* and *orphans*, which are less of a concern on the web without the concept of pages: > Isolated lines created when paragraphs _begin_ on the _last_ line of a > page are known as _orphans_. They have no past, but they do have a future, > and they need not trouble the typographer. The stub-ends left when > paragraphs _end_ on the _first_ line of a page are called _widows_. They > have a past but no future, and they look foreshortened and forlorn. [^short]: [Robert Bringhurst][The Elements of Typographic Style] dictates four as the minimum word length alone on the last line, but many prefer more than that. > _2.4.2._ Avoid leaving the stub-end of a hyphenated word, or any word > shorter than four letters as the last line of a paragraph. ![Line-breaking in Firefox 160](self://media/images/line-break.svg#firefox){.lf1-line-break} Unlike Firefox, Chromium 157 implements `text-wrap: pretty`. It [adjusts paragraphs ending with a word alone on the last line][pretty-chromium] by adjusting the break points for the last four lines to hold two last words together, like "_sifflements aigus_{lang=fr}" in our example. ![Line-breaking in Chromium 157](self://media/images/line-break.svg#chrome){.lf1-line-break} Like Firefox, WebKitGTK 2.54[^safari] may hyphenate "_aigus_{lang=fr}," leaving a very short _runt_ on the last line. With `text-wrap: pretty` and without justification, it often [creates shorter paragraphs][]. When enabling both pretty wrapping and justification, WebKitGTK performs worse than any other browser in this example as it inserts too much space. [^safari]: It should match the behavior of a recent Safari 26, except maybe on the hyphenation dictionary. ![Line-breaking in WebKitGTK 2.54](self://media/images/line-break.svg#webkit){.lf1-line-break} My solution is to insert **soft hyphens** ([U+00AD][shy]), except near the end of the paragraph, and to insert **non-breaking spaces** ([U+00A0][nbsp]) to meet the minimal requirement to prevent a runt. In my case, I set the limit to 8 characters, punctuation included. The animation below marks each non-breaking space with a purple triangle and every soft hyphen with a vertical red line.[^debug] With `hyphens: manual`, the browser may insert a line break anywhere a soft hyphen is present. [^debug]: To show these marks on any page of this blog, type ← ← s. ![Line-breaking in Firefox 160 with preprocessed text](self://media/images/line-break.svg#preprocess){.lf1-line-break} Such an approach cannot match a proper line-breaking algorithm, but it works in Firefox, prevents the shortened paragraphs in Safari, and sometimes provides better results than what Chromium did, as it allows hyphenation of "_sif‐fle‐ments_{lang=fr}." Moreover, all browsers will break lines at the same places: with `hyphens: auto`, each browser uses its own hyphenation dictionary and Safari ignores [`hyphenate-limit-chars`][hyphenate-limit-chars], while [the specification for `text-wrap: pretty`][css-text-4] leaves the algorithm to each browser. render the page][], etc. This looks like a good place to fix the HTML code to hyphenate words and insert non-breaking spaces. I also add a bit of typographic sugar: I convert the straight single quotes `'…'` and double quotes `"…"` to their curly equivalents: `‘…’` and `“…”`; I turn an ellipsis `...` into its dedicated equivalent `…`; I add a narrow non-breaking space before a double punctuation or between two groups of digits in French, like in "_Ça fait donc 501 622 731._{lang=fr}" We could implement these transformations with regular expressions and a hyphenation library like [Pyphen][]: ```python NNBSP = "\u202f" # NARROW NO-BREAK SPACE SHY = "\u00ad" # SOFT HYPHEN NBSP = "\u00a0" # NO-BREAK SPACE opening_quote = re.compile(r"""(? str: r"""Apply typographic rules to text. >>> typography('"Don\'t panic," he said.', "en_US") '“Don’t panic,”\xa0he\xa0said.' >>> typography("« Attendez ! »", "fr") '«\u202fAt\xadtendez\u202f!\u202f»' """ text = opening_quote.sub(lambda m: "‘" if m[1] == "'" else "“", text) text = closing_quote.sub(lambda m: "’" if m[1] == "'" else "”", text) text = space_before_punct.sub(NNBSP + r"\1", text) text = space_after_punct.sub("«" + NNBSP, text) text = text.replace("...", "…") # Hyphenation hyphenator = pyphen.Pyphen(lang=lang, left=2, right=3) text = word.sub(lambda m: hyphenator.inserted(m[0], SHY), text) # No line break in the last 8 characters text = last_chars.sub( lambda m: m[0].replace(SHY, "").replace(" ", NBSP), text ) return text ``` However, it breaks if we have HTML tags in the middle: ```html

We need to apply the transformations to the plain text and stitch the HTML markup back into the result. I use the [`lxml` library][lxml] to parse and manipulate HTML. Iterating over each block and extracting the text is straightforward, but we lose all the inner markup: ```python for block in root.iter("p", "li", "h1", "h2", "h3"): text = typography("".join(block.itertext()), "en_US") ``` Instead, we need to keep track of the position of each group of letters in a depth-first walk of the HTML tree. For example, we split the text from the previous HTML specimen into three slots: ```python slots = [ ["p.text", 0, 'I have read "'], ["a.text", 13, "Dune"], ["a.tail", 17, '".'], ] text = "".join(slot[2] for slot in slots) ``` We translate modifications to the text into a list of substitutions: start position, end position, and new text. ```python changes = [] for m in opening_quote.finditer(text): start, end = m.span(1) changes.append((start, end, "‘" if m[1] == "'" else "“")) for m in closing_quote.finditer(text): start, end = m.span(1) changes.append((start, end, "’" if m[1] == "'" else "”")) # changes = [(12, 13, "“"), (17, 18, "”")] ``` To apply a substitution, we locate the slot it applies to and update the text.[^position] [^position]: The example only shows same-length substitutions. To handle the general case, we must also refresh the positions. ```python for start, end, new in changes: slot = next(slot for slot in reversed(slots) if slot[1] <= start) offset = start - slot[1] slot[2] = slot[2][:offset] + new + slot[2][offset + end - start :] # slots = [["p.text", 0, "I have read “"], # ["a.text", 13, "Dune"], # ["a.tail", 17, "”."]] ``` We can stitch the modifications back into the HTML tree with a second depth-first walk, amending the text nodes when they are different from what we recorded in the slots. [lxml]: https://lxml.de "lxml: Processing XML and HTML with Python" ## Faster with Cython For this task, Python is not the fastest language on this side of the galaxy.[^jit] But we can significantly speed up some parts of the code with [Cython][], a compiler to turn Python code into C extensions. [^jit]: The Python JIT could have given good results. As it is [likely to be removed][jit], I didn't try. This lets the browser split a long IPv6 address, like `2a01:e0e:c03c:f44e:dabc:7337:38fa:ff40`, or a Python method name, like `xxhash.xxh3_128_hexdigest()`, at those markers. As far as I know, this is not something possible with just CSS. ## Copy/paste When copying text, some browsers may keep the soft hyphens or zero-width spaces. This is annoying when pasting into a terminal. We can intercept the "copy" event and strip these special characters from the `text/plain` version recorded in the clipboard: ```javascript document.addEventListener("copy", (event) => { const selection = document.getSelection(); const raw = selection.toString(); const text = raw // SOFT HYPHEN, ZERO WIDTH SPACE .replace(/[\u00ad\u200b]/g, "") // NO-BREAK SPACE, NARROW NO-BREAK SPACE .replace(/[\u00a0\u202f]/g, " "); if (text === raw) return; const div = document.createElement("div"); for (let i = 0; i < selection.rangeCount; i++) div.appendChild(selection.getRangeAt(i).cloneContents()); event.clipboardData.setData("text/plain", text); event.clipboardData.setData("text/html", div.innerHTML); event.preventDefault(); }); ``` Soft hyphens don't interfere with other features, like browsers' find-in-page or indexing by [Pagefind][].
